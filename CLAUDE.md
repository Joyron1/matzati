# CLAUDE.md — "מצאתי" (Matzati): Hebrew AI shopping assistant for AliExpress

> Working name: **מצאתי** ("Matzati"). The owner may rename it later, so keep the brand name in one config constant (`lib/config/brand.ts`).

## 1. What we are building

A Hebrew, RTL, mobile-first website where Israeli shoppers type what they need in free Hebrew
("אוזניות לריצה, עמידות למים, עד 100 ש״ח") and get **up to 10 vetted AliExpress products on the first view** (owner decision 2026-09-30, was 5: `RESULTS_FIRST_VIEW` in `lib/config/site.ts`): places 1-5 (`RESULTS_PER_PAGE`) each with a one-line Hebrew explanation of why it was picked, places 6-10 as standard cards with a Hebrew title and no line; then "show 5 more" (places 11-20).
Every product has an affiliate link and trust metrics.

Revenue comes from the AliExpress Affiliate Program (the owner already has an affiliate account).

Core product promises (never break these):
1. **Few, vetted results.** 10 on the first view (5 explained), then 5 at a time, and every one passed our filters.
2. **Honest data.** Every number shown (price, % positive feedback, units sold) comes from an AliExpress API response. Nothing invented. The only exceptions are what the owner enters in `/admin` and we label as ours: coupons ("לפי תנאי הקופון") and sale dates ("תאריכים לפי אלי אקספרס ולפי המועדים של השנים הקודמות": before AliExpress announces a sale, the owner enters the dates of earlier years and the sale's text says they are expected). No review text, no invented specs or descriptions.
3. **Transparent.** Affiliate disclosure next to every buy button (and every other link that goes to AliExpress through `/go`): a small "קישור שותפים" link to the full text in `/terms#affiliate` (owner decision 2026-09-28). Show which filters were applied and let the user remove them.

## 2. The golden architecture rule

**The LLM understands and explains. Code searches, filters and ranks.**

- The LLM never browses the web, never picks products freely, never invents facts or numbers.
- The LLM does exactly three jobs: (a) parse the Hebrew query into structured filters, (b) write a short Hebrew "why we picked it" line per result from the provided data only (and, for places 6-10 of the first view, a Hebrew product title only: `lib/llm/titles.ts`), (c) write generic per-category buying tips (cached per category).
- Search, filtering, ranking and link generation are deterministic TypeScript against the AliExpress Affiliate API.

## 3. Stack

- **Next.js (App Router) + TypeScript (strict) + Tailwind CSS**, deployed on **Vercel**.
- **Supabase (Postgres)** for cache, logs, deals, price history, admin auth.
- **LLM**: provider-agnostic interface in `lib/llm/` with two adapters:
  - Anthropic (default): official `@anthropic-ai/sdk`, model from env `LLM_MODEL` (default `claude-haiku-4-5-20251001`, a small fast model is enough for parsing).
  - OpenAI: **deferred (owner decision 2026-09-27)**. We run on Anthropic only; the interface in `lib/llm/provider.ts` stays provider-agnostic so an adapter can be added later without touching callers. Do not install `openai` until the owner asks.
  - Selected by env `LLM_PROVIDER=anthropic|openai`. Check the provider's current docs for model names instead of guessing.
- **Validation**: `zod` for every external input and every LLM output.
- **Tests**: `vitest`. **Lint/format**: ESLint + Prettier.
- Theme: `next-themes` (attribute `data-theme`).

Ask the owner before adding any other dependency.

## 5. AliExpress Affiliate API

### 5.1 Client (`lib/aliexpress/`)
- Gateway: `ALIEXPRESS_GATEWAY` (`https://api-sg.aliexpress.com/sync`).
- System params: `app_key`, `method`, `timestamp` (ms), `sign_method=sha256`, `sign`, plus method params.
- Signing: sort all params by key (ASCII), concatenate `key+value` pairs, HMAC-SHA256 with the app secret, hex uppercase.
- **Verify the signing details against the official AliExpress Open Platform docs before relying on them.** Write unit tests for the signer with a known example.
- Retries: 2 retries with backoff on network errors / 5xx. Timeout 8s. Map API error codes to typed errors.

- **Currency**: `ILS` may not be a supported `target_currency`. Try `ILS`; if rejected, request `USD` and convert with a daily USD→ILS rate (Bank of Israel official rates, cached daily in Supabase; fallback `USD_ILS_FALLBACK`). Show converted prices as approximate: `≈₪78`.
- **Price units** of `min_sale_price` / `max_sale_price` (whole units vs cents).
- **Response fields**: expected names include `product_id`, `product_title`, `target_sale_price`, `target_original_price`, `discount`, `evaluate_rate` (e.g. `"97.5%"`), `lastest_volume` (API spelling), `product_main_image_url`, `product_small_image_urls`, `product_detail_url`, `promotion_link`, `shop_id`, `shop_url`, `commission_rate`, `first_level_category_id`. Save one raw response per method to `fixtures/aliexpress/` (dev only, no secrets) and build zod schemas from real data.
- **Seller/store rating**: the affiliate API may not expose a store rating. **If no verified field exists, do not show any "seller reliability" number.** Our trust signals are then product positive-feedback % and units sold only.
- **Reviews**: review text is not available through the affiliate API. Do not build review summaries. Do not scrape AliExpress pages (violates their terms). The product page shows the API's numbers only and links to the reviews on AliExpress through `/go`.

## 6. Search pipeline — `POST /api/search`

Input: `{ q: string }` (1–200 chars, trimmed), optionally `cat`.

**Search inside a category** (owner request 2026-10-03): `/search?q=…&cat=<first-level id>` (the search box of a `/products` category page) and `cat` in the API body. `parseSearchCategory` (`lib/search-url.ts`) keeps only a first-level id with a whole-list catalog category (anything else is ignored). The parse is unchanged (cached and stored without it; `category_hint` as before); the filters then carry `category_id` (`SearchInput.category`), every `product.query` call sends `category_ids` (verified 2026-10-03: "usb cable" with `category_ids=44` gave 50 products, all first-level 44, against 27 of 50 without it), `canonicalFilters` adds `c` only when set (keys without a category are exactly as before) and the in-flight key adds it, so a category search never serves or joins the unrestricted one; it is logged in `search_log.parsed` with the filters (no migration); a category search that found nothing does not shorten the parse's cache life. `/search` shows a removable chip "בקטגוריה: <name>" first (removing it is the same query, sort and removed chips without `cat`, `categoryRemovedHref`), and every chip, sort, blocker and help link keeps `cat`. The crawler guard (`cachedSearchForBot` gets the category too), rate limits, "עוד N" (by `filters_key`) and listing on `/searches` (by query, unchanged) work as before.

1. **Guard**: validate, rate-limit per hashed IP (sha256 of IP + `IP_HASH_SALT`): 20 searches/hour, 100/day. Global kill switch: refuse new LLM work after `DAILY_SEARCH_CAP` searches/day and return a clear Hebrew message. **Crawlers never spend money** (owner request 2026-10-03): `/search` and `POST /api/search` check the user agent first (`isBotUserAgent` in `lib/guard/bots.ts`, a hand-kept list of search engines, AI crawlers and assistants, link previews, SEO tools, headless browsers and HTTP libraries; an empty user agent counts; tested true and false against real browser and in-app user agents) and call `cachedSearchForBot` (`lib/search/server.ts`), which runs the pipeline with `cacheOnly` (a cached parse and an exact cached result set whose first view has every line and title; no pool view, no fetch) and deps that cannot call the LLM or AliExpress (`NO_LLM`, a client whose fetch refuses, a budget that refuses). A hit is served as usual and logged with origin `bot` (never listed, left out of the stats); a miss (`CacheMissError`) writes no row and gets a short page (`app/search/bot-notice.tsx`: the live search runs for visitors, links to the home page, `/products` and the published landing pages; 200, noindex) or, from the API, 200 JSON `{error: "bots_only", ...}` with `X-Robots-Tag: noindex`. The per-IP limits apply to crawlers too. The WhatsApp webhook calls `searchForRequest` directly and is not checked.
2. **Cache (two levels, 14 days; owner decision 2026-09-27, was 48h; a result set with no products stays 48h, `EMPTY_RESULTS_TTL_HOURS`; a `degraded` one whose explain call failed, with English titles, only 1 hour, `DEGRADED_RESULTS_TTL_HOURS`, so the next searches get Hebrew)** — never trade accuracy for a hit (`lib/search/cache-key.ts`, `CACHE_TTL_DAYS`):
   - `parse_cache`: key = hash of the normalized query (spacing, niqqud, quotes, ש״ח/שקל/₪ unified). A hit skips the parse call. A parse whose own filters (no chip removed) found nothing is kept 48h too (`emptyParseCreatedAt` in `lib/search/pipeline.ts` stores it with an earlier `created_at`).
   - `search_cache`: key = hash of the canonical parsed filters (`canonicalFilters`: keyword words as a set; product terms and requirements in the parse's order, since the first of each drives relevance and the keyword steps; preference words; `category_hint`; the Hebrew labels explain writes with, misspellings fixed; rounded price bounds; sort; the shop cap mode the list is ranked under (§6.6); `RANKING_VERSION`, `EXPLAIN_VERSION`, `TITLES_VERSION` and `RESULTS_SHAPE` ("10/5/20": first view, explained page, kept), so a result set of the old shape (5 on the first view, 15 kept) is never served). A different phrasing that parses to identical filters reuses the results and explanations; only the parse call is paid.
   - No fuzzy or semantic text matching: reuse only when the filters that determine the results are identical.
   - The checked pool (plan item 13, `lib/search/pool.ts`): the result set a fetch was made for (the parse's own sort; a fetch for another sort writes that one too) keeps `pool`: every view the results page can reach without new products (the 3 sorts × every set of requirement chips removed), each ranked with `rankWithFill` over every product the fetch checked, so its order and counts are exactly what a fetch of that pool would give (ids, passed, blockers under a page), the products they show, the lines written for any of them (`pool.lines`) and the Hebrew titles the titles call wrote for any view's places 6-10 (`pool.titles`; the result set's own are `CachedResults.titles`). A title is never a line: it is kept in its own map, shown only in places 6-10, and a product that has only a title is explained like any product without a line once a view (another sort, a removed chip) shows it in places 1-5 (tested in `lib/search/pipeline-stages.test.ts`). A request with no exact hit is served from the pool of the result set fetched for the same chips, then of the one fetched before its requirements were removed: no parse, no product.query, and `isFreshResults` of that pool. A removed requirement is a view only when at least a page passes without it (otherwise it fetches again without its words, as before); a removed price bound always fetches again (the bounds were sent to AliExpress). Every view is saved as a result set of its own ("עוד N" works unchanged); `search_log.cache` "results" with `diag.derived`. A line written for another page of the pool is reused only after every explain check runs again against the products it is shown with (`lineThatHolds`: "הזול מבין החמישה" only if still true, and only on a page of five), never a data line, never a repeat; the rest are explained in one call and, beside reused lines, checked again against the whole page. Out of daily budget, a view that needed no fetch shows data lines (kept 48 h). `updateResults` writes only onto the entry it was read from (same `createdAt`).
3. **Parse (LLM)** → zod-validated JSON, schema in `lib/llm/parse.ts`, contract in `lib/search/filters.ts` (revised with the owner 2026-09-27):
   ```ts
   {
     keywords_en: string;          // 2–4 words the way sellers title the product (no gift/audience/praise words)
     product_terms: string[];      // 1–4 phrases naming the product itself: ["phone holder", "phone mount"]
     product_he: string;           // Hebrew product chip: "מחזיק טלפון לרכב"
     requirements: { en: string; alt: string[]; he: string }[]; // 0–3 stated hard requirements, ALL must match
     min_price_ils?: number;
     max_price_ils?: number;
     sort_preference: "best_value" | "cheapest" | "most_popular";
     category_hint?: string;       // used by the keyword fallback ladder
   }
   ```
   Temperature 0. One retry on invalid output; on second failure the search fails with a clear Hebrew message. Price chips are rendered by code from the numbers (`lib/search/chips.ts`), never by the LLM. `PARSE_VERSION` is part of the parse cache key.
   A character, franchise, team or brand the user named ("סוניק", "פרוזן", "מכבי") is always a requirement in its Latin spelling (`PARSE_VERSION` 7, 2026-09-30: "בלונים ליום הולדת של סוניק" found Pokémon balloons when "sonic" was only a keyword). An age or number for a birthday or party item ("יום הולדת 3", "בת 5", "גיל 40"; `PARSE_VERSION` 8, 2026-09-30, the schema's `preferences` field) is never a requirement: the keywords say it as sellers do ("sonic 3rd birthday balloons") and it becomes a **preference** whose words are whole seller phrases (`agePhrases`: "3rd birthday", "third birthday", "number 3", "3 years", "3 year old", "age 3"); code keeps only phrases that name the number, turns an age the model made a requirement into this preference (`age_preference` fix), and reads it from the Hebrew itself when the model left it out and the query names a birthday or party (`agePreferenceFrom`). With such a preference the product terms lose their number words (`withoutNumbers`, `PARSE_VERSION` 9: "number 5 balloon" turned away 61 of 119 gold number balloons titled "Gold Number Foil Balloons 0-9"): the number orders, it never decides what the product is. Code guards (`normalizeParsed`, plan item 8): an alt with another meaning (another feature group: "fast charging" under wireless charging) or one word of a longer requirement ("sensor" for motion sensor) is dropped; a description (over 2 words, or supports / compatible / multi-device / universal / and / or / a leading "for") becomes the known feature phrase inside it, else its first plain alt, else a **preference** (`SearchFilters.preferences`: no chip and no filter; its plain words count toward relevance coverage, a whole phrase (several words, or a number) only as a whole (`titleSaysPhrase` in `lib/ranking/relevance.ts`: never inside "3pcs", "3m", "3 in 1", "1-3 years" or "Number 30"), a preference the title states adds `WEIGHTS.preference` (1) times the share of preferences stated to the score, and `/search` says "את ״X״ לא סיננו, רק העדפנו מוצרים שהשם שלהם מזכיר את זה."); gift terms become sets ("cooking gift" → "cooking set"); the plain product is added (the term without audience words when two words remain, or a `PLAIN_PRODUCTS` noun such as "earbuds", never for an audience term like "kids headphones"); known misspellings of the Hebrew labels are fixed (`fixSpelling`).
4. **Fetch** (`lib/search/pipeline.ts`, the decisions in `lib/search/fetch-policy.ts`, plan item 5): `product.query` sorted by `LAST_VOLUME_DESC`, `ship_to_country=IL`, target ILS, price bounds in agorot. Keep fetching until the first view and a page pass (`TARGET_PASSED`, 15; owner decision 2026-09-30, was 10) or 4 calls (`MAX_ALI_CALLS`, was 3), spaced ~1.1 s (their frequency ban). Measured on the 32 snapshots (`npm run eval:offline -- --against ten-before`, 2026-09-30; `fixtures/snapshots/report-ten-before.json` / `report-ten-after.json`): 48 replayed calls instead of 44 (13 queries now want a call the snapshots lack, 8 before, so live searches make a few more), the first view shows 293 cards over 32 queries (9.2 per query; before, 5 per query were shown), 6 queries show fewer than 10 (8 had fewer than 10 passers before), "wrong" in the first view 8 → 7, page 1 unchanged in every query; each next call by what blocked: when relevance (type, requirement) rejected most, page 2 of the parse's keywords while it can still pass the trust bar (results come by sales, so a page 1 ending under 100 sales, FILL_TIER's 20 while fewer than the first view pass (`fillTo`; an SEO refresh: one page), ends that search); when trust rejected most, broader keywords first. Broader keywords (`keywordSteps`): without audience and gift words ("kids", unless the first product phrase has them), praise words and the number a preference names ("sonic 3rd birthday balloons" → "sonic birthday balloons"), then another product phrase with the main requirement, then `category_hint` with the main requirement ("naruto collectible figures"), and only then the steps without the requirement words (the keywords without them, the bare `category_hint`): a named character or brand seldom turns up by chance (live "Naruto pop", 2026-10-04: "pop figure" and "collectible figures" spent 2 of 4 calls on other anime; RANKING_VERSION 11). A requirement that none of the otherwise passing products mentions, with 100 or more checked and nothing passing, stops the search early (the page then offers to remove it). Only the first call can fail the search: a later one that fails keeps what was found, and no call after the first starts once the fetch has run 14 s (`FETCH_BUDGET_MS`, was 12 s). The offline replay runs the same function (`CURRENT_POLICY` in `lib/eval/policies.ts`, checked by `lib/eval/parity.test.ts`; `r5` is the rule before item 5).
5. **Filter** (`lib/ranking/`, config in `lib/ranking/config.ts`, defaults to be tuned):
   - `evaluate_rate` ≥ 90% and `lastest_volume` (30-day sales) ≥ 100 (`FILTERS`); missing values fail. When fewer than `FILL_UP_TO` (the first view, 10; owner decision 2026-09-30, was one page) pass, `FILL_TIER` (93% and 20 sales, owner decision 2026-09-30, was 95% and 30) tops the list up to 10, after every standard passer (`rankWithFill` / `rankForSearch`); an SEO refresh still fills one page. The UI, `/terms`, the FAQ, the home "איך זה עובד" and the waiting tips read these constants.
   - within price bounds (ILS only; prices are never compared across currencies)
   - type gate (`lib/ranking/type-gate.ts`): a `product_terms` phrase within the first 12 title words (numbers do not count), and not an accessory of it. Terms also match through narrow synonym groups and one-way kinds (`lib/ranking/synonyms.ts`: earbuds / earphones / headphones / headset, smartwatch / smart watch, a cutlery tray for a drawer organizer, an action or anime figure, figurine or blind box for a pop figure or funko pop (owner decision 2026-10-04: few Funko listings pass the trust bar, figures of the same character do; the character stays a requirement), ...); leading words of a longer term may stand before the product words or just after them ("Water Bottle For Kids"), not far past them and not inside "multi-color"; "X ... for <use>" counts as "<use> X". Out: an accessory noun before the term or right after it (organizer, case, sharpener, hook, ...), a holder noun right after it (stand, mount, bracket: a search naming one allows all), a cable right after a charger's name, an unsearched object (car, bike, Tesla, headrest, ...) opening the title, right before the term or right before any occurrence of the product's own noun ("... Car Charger"), a term that reaches across another thing's noun, a pasted category label, and pretend-play replicas unless the search is for kids or toys
   - every requirement matches the title (its `en`, any `alt`, or a code synonym; numeric specs like "65w" mean at least 65W); a "small" / "mini" search caps a capacity spec at 1.5 times it
6. **Rank** (`RANKING_VERSION` 11): device connectors (`lib/ranking/connectors.ts`, 2026-09-29): when a cable, charger or adapter search names a device whose port is known (iPhone 15 and newer: USB-C; iPhone 5-14 and SE: Lightning), a cable whose phone-end plug is the other connector fails the type gate and a title listing both connectors moves down; cases and screen protectors are never touched. Score = weighted positive-feedback (above 98% shrunk toward 98% for small samples) + log(volume) + price fit (every price fits fully inside a stated budget; the discount is shown, never scored) + relevance × 3 (`lib/ranking/relevance.ts`: where the product term starts, not made for an unsearched object, share of the search and preference words the title says, the first product term word for word). In the default sort, passers from another first-level category than two thirds of them go last and an exact asked capacity comes before a bigger one; "cheapest" orders by price and "most popular" by 30-day sales, whatever the category. Near-duplicate listings are removed (same shop and similar titles, same sales of 1,000+, near-identical titles across shops, model editions such as S32 / S32PRO). A preference the title states (`preferenceFit`, whole phrases, §6.3) adds `WEIGHTS.preference` (1: 5 points of positive feedback, about 4.6 times the sales) so a "Number 3" balloon passes comparable ones without it, never a clearly less trusted one or a standard passer (RANKING_VERSION 10, 2026-09-30). A search keeps `RESULTS_KEPT` (20, four pages of 5; was 15). **Shop cap: an admin setting** (owner decision 2026-09-28; `/admin/settings`, `site_settings` key `shop_cap`, `lib/settings/`): "none" (the default, and whenever the setting cannot be read) puts no limit on one shop, only the duplicate removal above; "max2" allows at most 2 products of one shop on the first page of 5 and 8 of the 20 kept, unless no other shop has one left (`SHOP_CAPS` in `lib/ranking/config.ts`, `diversifyShops` in `lib/ranking/diversity.ts`). The ranking takes the mode as an input (`rankWithFill`, the pool's views, the first-page safety net); `lib/search/server.ts` reads it once per request (`shopCapMode`, `unstable_cache` tag "settings", 5 minutes, the admin's save expires it with `updateTag`) into `SearchDeps.shopCap`; the results cache key and the in-flight key hold it, so a switch never serves a list ranked under the other mode, and the first searches after a switch fetch and explain again (the parse is reused). `/p`'s similar products look for the result set of the current mode, then of the other. The offline harness takes `--shop-cap none|max2|none,max2`. Measured on the snapshots (docs/search-quality-wave-a.md "Five results"): "none" shows more exact or reasonable cards but lets the shared-numbers store fill most first pages; "max2" spreads the page across shops.
   Shared numbers (owner decision 2026-09-28: trusted less by a general rule, never blocked; `lib/ranking/shared-numbers.ts`, `SHARED_NUMBERS`): judged over every product a search checked, a shop shares numbers when two of its listings show the same 30-day sales of 500 or more, or at least 5 of its listings have a feedback value and 80% of them show the same one below 100% (on the snapshots only shop 1103573332, "Stone's Store", at 98.0%). Its listings score feedback at most `FEEDBACK_PRIOR.pct`, and a sales number k of them share counts as sales/k (score and "most popular"); filters still read AliExpress's numbers. Each ranked listing of such a shop carries `sharedNumbers` (`ResultProduct.shared_numbers`: `feedback` when it shows the value its shop repeats, `sales` when another listing shows its exact sales); the card keeps AliExpress's numbers and says which are shared (`sharedNumbersNote` in `components/trust-metrics.tsx`), explain never gets a shared number (and its data sentence leaves it out: "עבר את הסינון שלנו." when both are), and a batch with such a listing allows no best-selling or best-rated claim. The mark is never stored in `products` (`withoutSharedMark` in `saveProducts`). Not applied to hot lists or `/p` yet.
   **Commission rate may only break exact ties. Never rank a worse product higher because it pays more.**
7. **Links**: use `promotion_link` if present; otherwise batch `link.generate`. A product we cannot link is not shown (when `link.generate` fails, the products that have a link go on; the search fails only when none has one).
   Search links never switch type by commission (always the query's link or type 0); only hot lists use type 2 hot links (§5.2).
8. **Explain (LLM)** (`lib/llm/explain.ts`): for the shown products (up to 5, one call per page), input = the displayed fields plus the search filters and their Hebrew labels. **Never the raw query**: explanations are cached 14 days by filters (owner decision 2026-09-27, was 48h) and reused for other users. Output per product: `title_he` and `why_he` (25–120 chars). Output cap `EXPLAIN_TOKENS` (256 + 256 per product: 1,536 for 5; the final paid check used at most ~107 output tokens per product).
   Comparisons stay within the batch shown (owner decision 2026-09-28): "הזול", "הנמכר ביותר" or "המשוב החיובי הגבוה ביותר" with the scope of the batch's size, "מבין החמישה" (5), "מבין הארבעה" (4), "מבין השלושה" (3), "מבין השניים" (2), none for one; code checks that the claim is true for that batch and that the scope names its size (`comparisonSizes` in `lib/llm/text-checks.ts`), and a line shown beside lines of another call is checked again with the whole page.
   Post-checks reject a line with an ungrounded number, a written price, a false or unverifiable superlative, singular address, foreign or mixed script, or truncation, "תקציב" when no budget was given, a known garbled word, or a line identical to an earlier one of the batch once its own numbers are set aside; a rejected `why_he` falls back to a sentence built from the data ("<pct>% משוב חיובי ו־<n> נמכרו ב־30 הימים האחרונים."). `title_he` is repaired rather than rejected: a Latin word stays only when the English title has it and it is a brand, model or spec, and a name the English title puts after "for" only when the Hebrew says "for" too (`lib/llm/text-checks.ts`); an English word the model wrote in Hebrew letters ("פלוש") becomes Hebrew ("מפרווה רכה"; `fixTransliterations`, `lib/transliterations.ts`, a small tested table, a spelling with another meaning only when the English title has the word). Since 2026-09-29 the same table fixes why-lines too, before the post-checks and at render time for cached lines. Titles already cached are read through the same table (`toResultProduct`, the recent-search photo alts, `/coupons`, `/p`'s similar products), so no cache bump is needed; AliExpress's own Hebrew titles (hot lists) go through it only without an English title (`hotTitle`, §5.2). Known misspellings are fixed in the labels, the explain input and the lines (`fixSpelling`). `EXPLAIN_VERSION` (6) is part of the results cache key.
   When the explain call itself fails, the products are shown with AliExpress's title and the data sentence, and the result set is cached `degraded` (1 hour, then searched and explained again); a "עוד N" page is shown that way without saving it. A first-page line that says its product is another product ("אביזר משלים", "לא <product_he>") moves that product off the first page (`demoteFlaggedLeads`, `lib/ranking/featured-guard.ts`); the one that moves up gets the data sentence, no extra call. A page whose every line is already known (a view whose lines all held) goes through it before its products show, so the streamed page never shows an order it then takes back. A product that moves up from place 6 keeps the Hebrew title it had there.
   **Titles of places 6-10** (owner decision 2026-09-30, `lib/llm/titles.ts`): the first view's places 6-10 get a Hebrew title only, from one cheaper titles call that runs beside the explain call (same stage; `LLM_STAGE_LIMITS.titles`, 10 s with 1 retry; temperature 0; output cap `TITLES_TOKENS` 128 + 96 per product, 608 for 5). Input: the English titles and the search's Hebrew labels (`product_he`, `requirements_he`), never the raw query; output `title_he` per product (zod), repaired and checked exactly as explain's titles (`checkTitle` in `lib/llm/explain.ts`, which `checkExplanation` uses too; the prompt shares explain's `TITLE_RULE` and `HEBREW_SCRIPT_RULE` word for word, so `EXPLAIN_VERSION` stays 6). A title already known (a line's, or one the titles call wrote for any view of the pool) needs no call. Recorded in `llm_usage` as `titles` and saved to `products.title_he`. When the call fails (or the budget is out for a view that needed no fetch), those cards show AliExpress's title and a new result set is cached `degraded` (1 hour), as after a failed explain call; a hit keeps its lines and asks again next time. `TITLES_VERSION` (1) is part of the results cache key. About $0.0017 a call (estimate, not measured live yet).
   **Streaming (plan item 15)**: `startSearch` runs a search in stages (`SearchStages`: the chips once understood; the products once ranked, linked and their rows saved, so `/go` works; the final response once every line is written and the result set cached; then the logs), `startSearchForRequest` in `lib/search/server.ts` gives the page these stages (none rejects; a request joining an identical run shares them with its own `search_uid`; the writes after the page are kept alive with `after()`), and `searchForRequest` (JSON API) waits for the final response. `/search` (owner request 2026-09-28) shows one waiting screen until the view is complete, then the whole results page at once, never a placeholder in a card: the page starts the search without waiting for it and passes its stages as promises to `components/search-view.tsx` (the chips once understood, shown inside the wait; the ranked products, when the wait marks reading, scanning, filtering and ranking done and makes "כותבים לכם למה בחרנו" current; the results rendered on the server once every line and every title of places 6-10 is written and the set cached, or with the lines from the data when explain failed, `app/search/results.tsx`). The wait (`components/search-wait/`, `schedule.ts`) marks a step done only on a real stage; between the chips and the products a schedule moves from scanning to filtering (past, never done), and ranking or writing are never claimed early. It sits beside the results, not as their Suspense fallback (a streamed fallback is not hydrated), and hides by CSS the moment the results are in the page (`globals.css`).
   Per-step LLM limits (`LLM_STAGE_LIMITS`): parse 10 s with 1 retry, then the search fails with `llm` ("השירות שמבין את החיפוש לא ענה בזמן", never "אלי אקספרס לא עונה"); explain 10 s with 1 retry (the Hebrew titles: visitor explain calls take 4.6 s at the median and 6.5 s at p90, and one at 10 s showed English titles), then the data fallback; titles 10 s with 1 retry, then AliExpress's titles; an SEO refresh plans its time around `seoExplain`, one 10 s try per group.
9. **Store**: `search_cache`, `search_log` (query, parsed filters, result ids, the first shown result's first-level `category_id`, `listable`; no IP, no user data), upsert `products` + a `price_history` row. ## 12. Working rules for Claude Code

- Code and comments in English; all user-facing text in Hebrew.
- Before calling any paid or quota-limited API in bulk (LLM, AliExpress), say how many calls you are about to make.
- Do not create cloud resources (Supabase projects, Vercel projects, domains) or anything with a cost without explicit owner approval.
- Never commit `.env.local`, fixtures containing secrets, or raw IPs. Save fixtures through `maskEnvValues` (`lib/mask.ts`); `lib/fixtures-secrets.test.ts` fails when a file under `fixtures/` holds an `.env.local` value of 8+ characters (it runs only where `.env.local` exists, and names the key and file, never the value).
- Run `npm run lint`, `npm run typecheck` and `npm test` before every commit.
- When an AliExpress field or behavior is uncertain, test it with the check script or read the official docs. Do not guess.
- Product photos never go through Vercel's image optimizer (`/_next/image`): Hobby allows 5,000 optimized source images a month and answers 402 past it, which broke every card on 2026-09-29. Every `next/image` goes through the site's loader (`images.loaderFile` in `next.config.ts` → `lib/image-loader.ts` → `aliImageUrl` in `lib/images.ts`): AliExpress's own resized copies (`<url>_<220|350|480|640>x<s>.jpg`, WebP); the video poster calls `aliImageUrl` itself. Never pass a `loader` prop from a server component: a function cannot cross into the client component, and the page 500s (2026-09-29).
- Page speed (Lighthouse mobile on `/`, 2026-09-30: 77 → 93-98). What holds it there, keep true: the CSS is inlined in every document (`experimental.inlineCss`; a separate stylesheet finished at ~1.5 s on a slow link and nothing painted before it); the first two hot-carousel photos are `preload` (eager, `fetchpriority=high`) and the image host is preconnected; the composer's turning border animates a transform on `::before`, never a gradient angle or another paint property (that repainted the frame 60 times a second for 27 s and delayed the largest paint); no `zod` in client-reachable modules (`lib/consent/*`); a `next/image` never gets a `loader` prop. Measure with the scratchpad Lighthouse scripts from `/tmp`, never from the project directory (chrome-launcher drops `C:\Users...` folders in the cwd and Turbopack then fails on them); a build that suddenly fails on a CSS module with "not pure" selectors is a stale `.next` cache. The remaining lab gap is the server response of the dynamic home page (TTFB and its variance) and the ~200 KB of JavaScript every page hydrates with.
- Keep functions small and pure where possible (`lib/ranking`, `lib/aliexpress/sign` are pure and fully unit-tested).
