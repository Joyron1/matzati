# CLAUDE.md — "מצאתי" (Matzati): Hebrew AI shopping assistant for AliExpress

> Working name: **מצאתי** ("Matzati"). The owner may rename it later, so keep the brand name in one config constant (`lib/config/brand.ts`).

## 1. What we are building

A Hebrew, RTL, mobile-first website where Israeli shoppers type what they need in free Hebrew
("אוזניות לריצה, עמידות למים, עד 100 ש״ח") and get **5 vetted AliExpress products** (plus "show 5 more"; owner decision 2026-09-28, was 3: `RESULTS_PER_PAGE` in `lib/config/site.ts`),
each with an affiliate link, trust metrics and a one-line Hebrew explanation of why it was picked.

Revenue comes from the AliExpress Affiliate Program (the owner already has an affiliate account).

Core product promises (never break these):
1. **Few, vetted results.** 5 at a time, and every one passed our filters.
2. **Honest data.** Every number shown (price, % positive feedback, units sold) comes from an AliExpress API response. Nothing invented. The only exceptions are what the owner enters in `/admin` and we label as ours: coupons ("לפי תנאי הקופון") and sale dates ("תאריכים לפי הודעת אלי אקספרס"). No review text, no invented specs or descriptions.
3. **Transparent.** Affiliate disclosure next to every buy button (and every other link that goes to AliExpress through `/go`): a small "קישור שותפים" link to the full text in `/terms#affiliate` (owner decision 2026-09-28). Show which filters were applied and let the user remove them.

## 2. The golden architecture rule

**The LLM understands and explains. Code searches, filters and ranks.**

- The LLM never browses the web, never picks products freely, never invents facts or numbers.
- The LLM does exactly three jobs: (a) parse the Hebrew query into structured filters, (b) write a short Hebrew "why we picked it" line per result from the provided data only, (c) write generic per-category buying tips (cached per category).
- Search, filtering, ranking and link generation are deterministic TypeScript against the AliExpress Affiliate API.

## 3. Stack

- **Next.js (App Router) + TypeScript (strict) + Tailwind CSS**, deployed on **Vercel**.
- **Supabase (Postgres)** for cache, logs, deals, price history, admin auth.
- **LLM**: provider-agnostic interface in `lib/llm/` with two adapters:
  - Anthropic (default): official `@anthropic-ai/sdk`, model from env `LLM_MODEL` (default `claude-haiku-4-5-20251001`, a small fast model is enough for parsing).
  - OpenAI: **deferred (owner decision 2026-09-27)**. We run on Anthropic only; the interface in `lib/llm/provider.ts` stays provider-agnostic so an adapter can be added later without touching callers. Do not install `openai` until the owner asks.
  - Selected by env `LLM_PROVIDER=anthropic|openai`. Check the provider's current docs for model names instead of guessing.
- **Validation**: `zod` for every external input and every LLM output.
- **Tests**: `vitest`. **Lint/format**: ESLint + Prettier.
- Theme: `next-themes` (attribute `data-theme`).

Ask the owner before adding any other dependency.

## 5. AliExpress Affiliate API

### 5.1 Client (`lib/aliexpress/`)
- Gateway: `ALIEXPRESS_GATEWAY` (`https://api-sg.aliexpress.com/sync`).
- System params: `app_key`, `method`, `timestamp` (ms), `sign_method=sha256`, `sign`, plus method params.
- Signing: sort all params by key (ASCII), concatenate `key+value` pairs, HMAC-SHA256 with the app secret, hex uppercase.
- **Verify the signing details against the official AliExpress Open Platform docs before relying on them.** Write unit tests for the signer with a known example.
- Retries: 2 retries with backoff on network errors / 5xx. Timeout 8s. Map API error codes to typed errors.

Never call `revalidatePath("/")`: it expires the cached hot lists `/` reads (the next view refetches 4 lists with no stale fallback); the home sections read tagged caches, so admin actions use `updateTag` |

Verified behavior, access per method and request ids: `docs/aliexpress-api.md`. Confirm a newly granted permission with one call before turning its flag on.

Common params: `keywords`, `page_no`, `page_size` (50), `sort` (e.g. `LAST_VOLUME_DESC`), `target_currency`, `target_language` (`HE`), `ship_to_country=IL`, `tracking_id`, `min_sale_price` / `max_sale_price`.

### 5.3 Things to verify with real calls (do NOT assume)
- **Currency**: `ILS` may not be a supported `target_currency`. Try `ILS`; if rejected, request `USD` and convert with a daily USD→ILS rate (Bank of Israel official rates, cached daily in Supabase; fallback `USD_ILS_FALLBACK`). Show converted prices as approximate: `≈₪78`.
- **Price units** of `min_sale_price` / `max_sale_price` (whole units vs cents).
- **Response fields**: expected names include `product_id`, `product_title`, `target_sale_price`, `target_original_price`, `discount`, `evaluate_rate` (e.g. `"97.5%"`), `lastest_volume` (API spelling), `product_main_image_url`, `product_small_image_urls`, `product_detail_url`, `promotion_link`, `shop_id`, `shop_url`, `commission_rate`, `first_level_category_id`. Save one raw response per method to `fixtures/aliexpress/` (dev only, no secrets) and build zod schemas from real data.
- **Seller/store rating**: the affiliate API may not expose a store rating. **If no verified field exists, do not show any "seller reliability" number.** Our trust signals are then product positive-feedback % and units sold only.
- **Reviews**: review text is not available through the affiliate API. Do not build review summaries. Do not scrape AliExpress pages (violates their terms). The product page shows the API's numbers only and links to the reviews on AliExpress through `/go`.

## 6. Search pipeline — `POST /api/search`

Input: `{ q: string }` (1–200 chars, trimmed).

1. **Guard**: validate, rate-limit per hashed IP (sha256 of IP + `IP_HASH_SALT`): 20 searches/hour, 100/day. Global kill switch: refuse new LLM work after `DAILY_SEARCH_CAP` searches/day and return a clear Hebrew message.
2. **Cache (two levels, 14 days; owner decision 2026-09-27, was 48h; a result set with no products stays 48h, `EMPTY_RESULTS_TTL_HOURS`, and so does a `degraded` one whose explain call failed)** — never trade accuracy for a hit (`lib/search/cache-key.ts`, `CACHE_TTL_DAYS`):
   - `parse_cache`: key = hash of the normalized query (spacing, niqqud, quotes, ש״ח/שקל/₪ unified). A hit skips the parse call. A parse whose own filters (no chip removed) found nothing is kept 48h too (`emptyParseCreatedAt` in `lib/search/pipeline.ts` stores it with an earlier `created_at`).
   - `search_cache`: key = hash of the canonical parsed filters (`canonicalFilters`: keyword words as a set; product terms and requirements in the parse's order, since the first of each drives relevance and the keyword steps; preference words; `category_hint`; the Hebrew labels explain writes with, misspellings fixed; rounded price bounds; sort; the shop cap mode the list is ranked under (§6.6); `RANKING_VERSION`, `EXPLAIN_VERSION`). A different phrasing that parses to identical filters reuses the results and explanations; only the parse call is paid.
   - No fuzzy or semantic text matching: reuse only when the filters that determine the results are identical.
   - The checked pool (plan item 13, `lib/search/pool.ts`): the result set a fetch was made for (the parse's own sort; a fetch for another sort writes that one too) keeps `pool`: every view the results page can reach without new products (the 3 sorts × every set of requirement chips removed), each ranked with `rankWithFill` over every product the fetch checked, so its order and counts are exactly what a fetch of that pool would give (ids, passed, blockers under a page), the products they show, and the lines written for any of them (`pool.lines`). A request with no exact hit is served from the pool of the result set fetched for the same chips, then of the one fetched before its requirements were removed: no parse, no product.query, and `isFreshResults` of that pool. A removed requirement is a view only when at least a page passes without it (otherwise it fetches again without its words, as before); a removed price bound always fetches again (the bounds were sent to AliExpress). Every view is saved as a result set of its own ("עוד N" works unchanged); `search_log.cache` "results" with `diag.derived`. A line written for another page of the pool is reused only after every explain check runs again against the products it is shown with (`lineThatHolds`: "הזול מבין החמישה" only if still true, and only on a page of five), never a data line, never a repeat; the rest are explained in one call and, beside reused lines, checked again against the whole page. Out of daily budget, a view that needed no fetch shows data lines (kept 48 h). `updateResults` writes only onto the entry it was read from (same `createdAt`).
3. **Parse (LLM)** → zod-validated JSON, schema in `lib/llm/parse.ts`, contract in `lib/search/filters.ts` (revised with the owner 2026-09-27):
   ```ts
   {
     keywords_en: string;          // 2–4 words the way sellers title the product (no gift/audience/praise words)
     product_terms: string[];      // 1–4 phrases naming the product itself: ["phone holder", "phone mount"]
     product_he: string;           // Hebrew product chip: "מחזיק טלפון לרכב"
     requirements: { en: string; alt: string[]; he: string }[]; // 0–3 stated hard requirements, ALL must match
     min_price_ils?: number;
     max_price_ils?: number;
     sort_preference: "best_value" | "cheapest" | "most_popular";
     category_hint?: string;       // used by the keyword fallback ladder
   }
   ```
   Temperature 0. One retry on invalid output; on second failure the search fails with a clear Hebrew message. Price chips are rendered by code from the numbers (`lib/search/chips.ts`), never by the LLM. `PARSE_VERSION` is part of the parse cache key.
   Code guards (`normalizeParsed`, `PARSE_VERSION` 6, plan item 8): an alt with another meaning (another feature group: "fast charging" under wireless charging) or one word of a longer requirement ("sensor" for motion sensor) is dropped; a description (over 2 words, or supports / compatible / multi-device / universal / and / or / a leading "for") becomes the known feature phrase inside it, else its first plain alt, else a **preference** (`SearchFilters.preferences`: no chip and no filter; its title words count toward relevance, and `/search` says "את ״X״ לא סיננו, רק העדפנו מוצרים שהשם שלהם מזכיר את זה."); gift terms become sets ("cooking gift" → "cooking set"); the plain product is added (the term without audience words when two words remain, or a `PLAIN_PRODUCTS` noun such as "earbuds", never for an audience term like "kids headphones"); known misspellings of the Hebrew labels are fixed (`fixSpelling`).
4. **Fetch** (`lib/search/pipeline.ts`, the decisions in `lib/search/fetch-policy.ts`, plan item 5): `product.query` sorted by `LAST_VOLUME_DESC`, `ship_to_country=IL`, target ILS, price bounds in agorot. Keep fetching until two pages pass (`TARGET_PASSED`, 10 for pages of 5; measured on the snapshots 2026-09-28: 44 replayed calls instead of 38 for 6, docs/search-quality-wave-a.md "Five results") or 3 calls, spaced ~1.1 s (their frequency ban); each next call by what blocked: when relevance (type, requirement) rejected most, page 2 of the parse's keywords while it can still pass the trust bar (results come by sales, so a page 1 ending under 100 sales, 30 while fewer than a page pass, ends that search); when trust rejected most, broader keywords first. Broader keywords (`keywordSteps`): without audience and gift words ("kids", unless the first product phrase has them) and praise words, then also without requirement words, then another product phrase with the main requirement, then `category_hint`. A requirement that none of the otherwise passing products mentions, with 100 or more checked and nothing passing, stops the search early (the page then offers to remove it). Only the first call can fail the search: a later one that fails keeps what was found, and no call after the first starts once the fetch has run 12 s (`FETCH_BUDGET_MS`). The offline replay runs the same function (`CURRENT_POLICY` in `lib/eval/policies.ts`, checked by `lib/eval/parity.test.ts`; `r5` is the rule before item 5).
5. **Filter** (`lib/ranking/`, config in `lib/ranking/config.ts`, defaults to be tuned):
   - `evaluate_rate` ≥ 90% and `lastest_volume` (30-day sales) ≥ 100; missing values fail
   - within price bounds (ILS only; prices are never compared across currencies)
   - type gate (`lib/ranking/type-gate.ts`): a `product_terms` phrase within the first 12 title words (numbers do not count), and not an accessory of it. Terms also match through narrow synonym groups and one-way kinds (`lib/ranking/synonyms.ts`: earbuds / earphones / headphones / headset, smartwatch / smart watch, a cutlery tray for a drawer organizer, ...); leading words of a longer term may stand before the product words or just after them ("Water Bottle For Kids"), not far past them and not inside "multi-color"; "X ... for <use>" counts as "<use> X". Out: an accessory noun before the term or right after it (organizer, case, sharpener, hook, ...), a holder noun right after it (stand, mount, bracket: a search naming one allows all), a cable right after a charger's name, an unsearched object (car, bike, Tesla, headrest, ...) opening the title, right before the term or right before any occurrence of the product's own noun ("... Car Charger"), a term that reaches across another thing's noun, a pasted category label, and pretend-play replicas unless the search is for kids or toys
   - every requirement matches the title (its `en`, any `alt`, or a code synonym; numeric specs like "65w" mean at least 65W); a "small" / "mini" search caps a capacity spec at 1.5 times it
6. **Rank** (`RANKING_VERSION` 9): device connectors (`lib/ranking/connectors.ts`, 2026-09-29): when a cable, charger or adapter search names a device whose port is known (iPhone 15 and newer: USB-C; iPhone 5-14 and SE: Lightning), a cable whose phone-end plug is the other connector fails the type gate and a title listing both connectors moves down; cases and screen protectors are never touched. Score = weighted positive-feedback (above 98% shrunk toward 98% for small samples) + log(volume) + price fit (every price fits fully inside a stated budget; the discount is shown, never scored) + relevance × 3 (`lib/ranking/relevance.ts`: where the product term starts, not made for an unsearched object, share of the search and preference words the title says, the first product term word for word). In the default sort, passers from another first-level category than two thirds of them go last and an exact asked capacity comes before a bigger one; "cheapest" orders by price and "most popular" by 30-day sales, whatever the category. Near-duplicate listings are removed (same shop and similar titles, same sales of 1,000+, near-identical titles across shops, model editions such as S32 / S32PRO). A search keeps `RESULTS_KEPT` (15, three pages of 5). **Shop cap: an admin setting** (owner decision 2026-09-28; `/admin/settings`, `site_settings` key `shop_cap`, `lib/settings/`): "none" (the default, and whenever the setting cannot be read) puts no limit on one shop, only the duplicate removal above; "max2" allows at most 2 products of one shop on the first page of 5 and 6 of the 15 kept, unless no other shop has one left (`SHOP_CAPS` in `lib/ranking/config.ts`, `diversifyShops` in `lib/ranking/diversity.ts`). The ranking takes the mode as an input (`rankWithFill`, the pool's views, the first-page safety net); `lib/search/server.ts` reads it once per request (`shopCapMode`, `unstable_cache` tag "settings", 5 minutes, the admin's save expires it with `updateTag`) into `SearchDeps.shopCap`; the results cache key and the in-flight key hold it, so a switch never serves a list ranked under the other mode, and the first searches after a switch fetch and explain again (the parse is reused). `/p`'s similar products look for the result set of the current mode, then of the other. The offline harness takes `--shop-cap none|max2|none,max2`. Measured on the snapshots (docs/search-quality-wave-a.md "Five results"): "none" shows more exact or reasonable cards but lets the shared-numbers store fill most first pages; "max2" spreads the page across shops.
   Shared numbers (owner decision 2026-09-28: trusted less by a general rule, never blocked; `lib/ranking/shared-numbers.ts`, `SHARED_NUMBERS`): judged over every product a search checked, a shop shares numbers when two of its listings show the same 30-day sales of 500 or more, or at least 5 of its listings have a feedback value and 80% of them show the same one below 100% (on the snapshots only shop 1103573332, "Stone's Store", at 98.0%). Its listings score feedback at most `FEEDBACK_PRIOR.pct`, and a sales number k of them share counts as sales/k (score and "most popular"); filters still read AliExpress's numbers. Each ranked listing of such a shop carries `sharedNumbers` (`ResultProduct.shared_numbers`: `feedback` when it shows the value its shop repeats, `sales` when another listing shows its exact sales); the card keeps AliExpress's numbers and says which are shared (`sharedNumbersNote` in `components/trust-metrics.tsx`), explain never gets a shared number (and its data sentence leaves it out: "עבר את הסינון שלנו." when both are), and a batch with such a listing allows no best-selling or best-rated claim. The mark is never stored in `products` (`withoutSharedMark` in `saveProducts`). Not applied to hot lists or `/p` yet.
   **Commission rate may only break exact ties. Never rank a worse product higher because it pays more.**
7. **Links**: use `promotion_link` if present; otherwise batch `link.generate`. A product we cannot link is not shown (when `link.generate` fails, the products that have a link go on; the search fails only when none has one).
   Search links never switch type by commission (always the query's link or type 0); only hot lists use type 2 hot links (§5.2).
8. **Explain (LLM)** (`lib/llm/explain.ts`): for the shown products (up to 5, one call per page), input = the displayed fields plus the search filters and their Hebrew labels. **Never the raw query**: explanations are cached 14 days by filters (owner decision 2026-09-27, was 48h) and reused for other users. Output per product: `title_he` and `why_he` (25–120 chars). Output cap `EXPLAIN_TOKENS` (256 + 256 per product: 1,536 for 5; the final paid check used at most ~107 output tokens per product).
   Comparisons stay within the batch shown (owner decision 2026-09-28): "הזול", "הנמכר ביותר" or "המשוב החיובי הגבוה ביותר" with the scope of the batch's size, "מבין החמישה" (5), "מבין הארבעה" (4), "מבין השלושה" (3), "מבין השניים" (2), none for one; code checks that the claim is true for that batch and that the scope names its size (`comparisonSizes` in `lib/llm/text-checks.ts`), and a line shown beside lines of another call is checked again with the whole page.
   Post-checks reject a line with an ungrounded number, a written price, a false or unverifiable superlative, singular address, foreign or mixed script, or truncation, "תקציב" when no budget was given, a known garbled word, or a line identical to an earlier one of the batch once its own numbers are set aside; a rejected `why_he` falls back to a sentence built from the data ("<pct>% משוב חיובי ו־<n> נמכרו ב־30 הימים האחרונים."). `title_he` is repaired rather than rejected: a Latin word stays only when the English title has it and it is a brand, model or spec, and a name the English title puts after "for" only when the Hebrew says "for" too (`lib/llm/text-checks.ts`); an English word the model wrote in Hebrew letters ("פלוש") becomes Hebrew ("מפרווה רכה"; `fixTransliterations`, `lib/transliterations.ts`, a small tested table, a spelling with another meaning only when the English title has the word). Since 2026-09-29 the same table fixes why-lines too, before the post-checks and at render time for cached lines. Titles already cached are read through the same table (`toResultProduct`, the recent-search photo alts, `/coupons`, `/p`'s similar products), so no cache bump is needed; AliExpress's own Hebrew titles (hot lists) go through it only without an English title (`hotTitle`, §5.2). Known misspellings are fixed in the labels, the explain input and the lines (`fixSpelling`). `EXPLAIN_VERSION` (6) is part of the results cache key.
   When the explain call itself fails, the products are shown with AliExpress's title and the data sentence, and the result set is cached `degraded` (48h); a "עוד N" page is shown that way without saving it. A first-page line that says its product is another product ("אביזר משלים", "לא <product_he>") moves that product off the first page (`demoteFlaggedLeads`, `lib/ranking/featured-guard.ts`); the one that moves up gets the data sentence, no extra call. A page whose every line is already known (a view whose lines all held) goes through it before its products show, so the streamed page never shows an order it then takes back.
   **Streaming (plan item 15)**: `startSearch` runs a search in stages (`SearchStages`: the chips once understood; the products once ranked, linked and their rows saved, so `/go` works; the final response once every line is written and the result set cached; then the logs), `startSearchForRequest` in `lib/search/server.ts` gives the page these stages (none rejects; a request joining an identical run shares them with its own `search_uid`; the writes after the page are kept alive with `after()`), and `searchForRequest` (JSON API) waits for the final response. `/search` (owner request 2026-09-28) shows one waiting screen until the view is complete, then the whole results page at once, never a placeholder in a card: the page starts the search without waiting for it and passes its stages as promises to `components/search-view.tsx` (the chips once understood, shown inside the wait; the ranked products, when the wait marks reading, scanning, filtering and ranking done and makes "כותבים לכם למה בחרנו" current; the results rendered on the server once every line is written and the set cached, or with the lines from the data when explain failed, `app/search/results.tsx`). The wait (`components/search-wait/`, `schedule.ts`) marks a step done only on a real stage; between the chips and the products a schedule moves from scanning to filtering (past, never done), and ranking or writing are never claimed early. It sits beside the results, not as their Suspense fallback (a streamed fallback is not hydrated), and hides by CSS the moment the results are in the page (`globals.css`).
   Per-step LLM limits (`LLM_STAGE_LIMITS`): parse 10 s with 1 retry, then the search fails with `llm` ("השירות שמבין את החיפוש לא ענה בזמן", never "אלי אקספרס לא עונה"); explain 10 s, no retry, then the data fallback.
9. **Store**: `search_cache`, `search_log` (query, parsed filters, result ids, the first shown result's first-level `category_id`, `listable`; no IP, no user data), upsert `products` + a `price_history` row. A fetch saves every product it kept (`RESULTS_KEPT`, all linked) in one batch before its cards show, `title_he` only for the lines written (the page's, saved after explain), so later pages and `/p`'s similar products (up to 8) have rows; a view or a hit saves only its page, as before. `listable` (`isListableSearch` in `lib/search/pipeline.ts`) is true only for a query the visitor typed (source `search`; not a recent-search card or an example link, which carry `from=recent` / `from=example`; no chips removed; no sort override) that showed results and whose query passes `lib/recent/privacy.ts`; `/searches` lists only those, with the search time rounded down to the hour. Each row also records (`20260928140000_search_telemetry.sql`) its `env` (`VERCEL_ENV`, `deployEnv` in `lib/env.ts`), `origin` (typed, example, recent, chip, sort, more, preview, ad for `utm_source`/`gclid` landings; `parseArrival` in `lib/search-url.ts`), the removed chips, the sort override, step `timings`, `ali_calls`, `rejected` counts and `failure` (a failed search writes a row too; a rate-limited request does not), and a `search_uid` made before the insert: the result cards' `/go` links carry it with the card's position (`s=`, `pos=`, validated with zod and used for logging only). A request that joins an identical search in flight logs its own row with `shared` true. A request made while a signed-in admin browses (`getAdminUser`) is logged with `owner` true (searches and clicks) and never counted in the stats; the owner's typed searches are real searches and are listed like anyone's (owner decision 2026-09-29: `owner` no longer blocks `listable`). A search that fetched, explained or ranked a view itself also writes `diag` (why fetching stopped, the keyword steps tried, the products the safety net moved down, explain fallbacks, `derived` for a view ranked from a checked pool and `lines_reused`). Outside production the parse and results caches are written under `dev:` / `preview:` keys (`SupabaseStore`): dev may read production's entries but never writes them, and production keys stay the bare hashes; the guard counters get the same prefix (`dev:llm:day`, `dev:h:<hash>`), and `products` gets new rows only (never an update of a row production serves, no `price_history`). A script that must write production's cache (the A11 warm-up) passes `new SupabaseStore(db, { env: "production" })` and runs as the owner, or its rows count as visitors'.
10. **Respond**: `{ query, chips, sort, checked_count, passed_count, results: [...5], more_available, filters_key, cached, fetched_at }`. `fetched_at` is when the results were fetched from AliExpress (the cache entry's time); `/search` shows "התוצאות והמחירים נבדקו ב־..." once it is older than `STALE_RESULTS_HOURS` (24, `lib/config/site.ts`). "עוד 5 אפשרויות" explains the next 5 on demand (`loadMore`; pages 2 and 3 of the 15 kept). With fewer than a page (5) of results, `blockers` (plan item 12, `lib/ranking/blockers.ts`): each removable filter whose removal lets more of the checked products pass, with how many, most useful first; `/search` shows "אף מוצר שבדקנו לא מציין בכותרת ״X״. בלי הסינון הזה היו עוברים N מהמוצרים שכבר בדקנו." with a remove button (1-4 results: one hint under them; a capacity of a "small" search says "... או עד פי 1.5 ממנו (ביקשתם מוצר קטן)"). Only the count is shown, never a product that failed a filter. With no single blocker and a removable requirement, the page advises removing a filter. `not_filtered`: the Hebrew labels of the parse's preferences (stated needs no title check can verify), named under the chips. Products that passed but none of which can be linked fail the search as `upstream`, never "none passed".

"Remove a chip" = the search with that chip id in `without`; the cached parse is reused, so there is no LLM parse call, and a removed requirement is served from the checked pool when a page passes without it (§6.2). Otherwise it searches again, and a removed requirement's words also leave the AliExpress keywords (`applyOverrides` in `lib/search/chips.ts`), except words a kept requirement or the first product phrase uses. On `/search` a sort change or a removed chip keeps the chips and results on screen, busy and dimmed with a dot on the link and a small centered "מעדכנים…" note ("כותבים לכם למה בחרנו…" once the page knows its lines are being written), until the next view is complete, then replaces them in one step (`components/search-view.tsx`); only one whose products are not ranked 700 ms after the click (a new AliExpress fetch) shows the wait instead, with its real stages.

## 12. Working rules for Claude Code

- Code and comments in English; all user-facing text in Hebrew.
- Before calling any paid or quota-limited API in bulk (LLM, AliExpress), say how many calls you are about to make.
- Do not create cloud resources (Supabase projects, Vercel projects, domains) or anything with a cost without explicit owner approval.
- Never commit `.env.local`, fixtures containing secrets, or raw IPs. Save fixtures through `maskEnvValues` (`lib/mask.ts`); `lib/fixtures-secrets.test.ts` fails when a file under `fixtures/` holds an `.env.local` value of 8+ characters (it runs only where `.env.local` exists, and names the key and file, never the value).
- Run `npm run lint`, `npm run typecheck` and `npm test` before every commit.
- When an AliExpress field or behavior is uncertain, test it with the check script or read the official docs. Do not guess.
- Product photos never go through Vercel's image optimizer (`/_next/image`): Hobby allows 5,000 optimized source images a month and answers 402 past it, which broke every card on 2026-09-29. Every `next/image` goes through the site's loader (`images.loaderFile` in `next.config.ts` → `lib/image-loader.ts` → `aliImageUrl` in `lib/images.ts`): AliExpress's own resized copies (`<url>_<220|350|480|640>x<s>.jpg`, WebP); the video poster calls `aliImageUrl` itself. - Keep functions small and pure where possible (`lib/ranking`, `lib/aliexpress/sign` are pure and fully unit-tested).
